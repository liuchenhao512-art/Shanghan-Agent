## 一、项目定位（已确认共识）

- **是什么**：网页端《伤寒论》教学知识库。学生逐条读原文和九家注解读，建立开阔的伤寒学术视野；并可用自然语言向 AI 查条文、查注家观点、做启发式问答。
- **给谁用**：成都中医药大学校内课程试点（几十~几百人），不公网开放，无需备案。
- **建设者**：教研室教师（用户，负责学术决策与审核）+ Claude（负责全部工程实现）。
- **节奏**：无硬性时间节点，质量优先，尽快出 demo。demo 先本机运行（localhost 一键启动），验证后迁校内服务器（内网免备案）。

## 三、核心设计决策（已确认）

1. **双视图**：主视图按宋本 398 条逐条集注（九家解读**可折叠**）；副视图保留各书原编次（错简重订等编次本身是学术主张），两边互相跳转。
2. **文字规范**：展示层统一简体（OpenCC + 中医专名词表防误转；通假字、生僻字保留原貌）；数据层保留抓取的繁体原文作存档字段。基准条文用《三家注》所载通行本 1–398 条（参刘渡舟《伤寒论校注》）；各家书内条文异文在该家视图内如实保留。检索做繁简归一。
3. **条文对齐审核**：自动文本匹配为主（预计解决 85–95%）；拆条/并条/改字等低置信条目生成**待审清单**交用户裁定；demo 上未裁定条目标"对齐待审"。
4. **AI 分层标注**：条文与注家论断必须基于库内检索回答并附可点击出处（条号+医家+原文片段），查无则明说；医史背景等通识可答但标注"库外知识"；临床诊疗问题一律不答、引导回学习场景。定位是启发思考（苏格拉底式引导优先于直接给答案）。
5. **第一版功能**：①逐条集注阅读 ②原书编次阅读 ③AI 对话 ④方剂索引（113方：组成煎服法+各家方论）⑤全文检索（按医家/篇章筛选）。**未来规划**：学生账号+笔记收藏、教师内容后台、繁简界面切换。
6. **大模型**：DeepSeek API（OpenAI 兼容接口封装，日后可切换 Qwen 等）。**API key 存于本目录 `.env` 文件（勿外传、勿提交 git）**。

## 四、技术方案（Claude 决定，用户无需关心）

- 环境：Windows 11，Python 3.12.10，Node 26（备用）。
- 后端：Python + FastAPI + uvicorn；数据 SQLite（FTS5 做全文检索）+ JSON 源文件。
- 前端：静态 HTML/CSS/JS（FastAPI 托管），不依赖联网 CDN。
- AI：后端代理调用 DeepSeek（deepseek-chat），结构化检索（条号/医家/方名直查）+ FTS 检索兜底，检索结果注入上下文，强制引用出处。
- 启动：`启动知识库.bat` 一键起服务并打开浏览器。

## 五、数据模型（草案，实现时细化）

- `passages` 条文：num(1–398)、篇章、基准原文(简)、繁体存档、校勘注
- `commentators` 注家：姓名、朝代、派别、著作、底本、来源URL
- `comments` 注文：passage_num、commentator、分段号(〔1〕〔2〕)、简体文、繁体存档、原书位置(卷/篇/序)、对齐方式(auto/confirmed/pending)
- `book_structure` 原书编次树：支撑副视图（卷→篇→条目顺序）
- `formulas` 方剂：方名、组成、煎服法、关联条文、各家方论
- SQLite FTS5 索引：条文+注文全文（简体归一）

## 九、桌面智能体客户端需求 2026-10-08

本节记录本轮用户已确认的新需求，不更改前述历史实现状态。详细实施提案与验收条件见[桌面智能体客户端第一版方案](桌面智能体客户端第一版方案.md)，整体方案待确认。

- **使用模式**：教师和学生等各自安装，保留全部现有功能，个人新增资料分别管理；首版同时支持 Windows 和 macOS。
- **专题组织**：用户自由建立多个专题库，任务可选择一个或多个知识库作为资料来源。
- **智能体能力**：现有问答属于已有能力；新增自主研读任务和知识库管理，三类能力均需要。
- **导入**：文字版 PDF、EPUB、Word、TXT、Markdown 及用户提供的网页/公众号文章链接。
- **扫描件**：提示需要额外文字识别处理及潜在时间/费用，可建议用 MinerU 等外部工具转换为 Markdown 后导入；第一版不内置扫描识别服务。
- **保存与模型**：本地保存，支持备份、导出与迁移，首版无账号和自动同步；各用户自行配置在线模型/API Key 并承担费用。
- **管理边界**：先分析、提出方案并预览，用户确认后才正式写入或修改知识库；检索、阅读和分析可自动连续进行。
- **研究场景**：首个验收场景为学术专题研究，形成有原文依据的共识、分歧、专题笔记及比较表。
- **依据边界**：专题研究严格限定用户所选知识库，资料不足时说明缺口并提示补充，不主动联网寻找资料。
- **成果格式**：笔记、专题报告及比较表支持 MD 和 PDF 导出；与整个知识库的备份迁移分别设计。
- **本次产物**：需求与实施提案文档，未改动应用代码或语料，未完成桌面打包或新功能验证。
